# ZOQO Alpha: runbook

Operational how-to for a human running Alpha day to day. For "what is this system and why," read `docs/alpha/03-architecture.md`; for "what's actually built vs. documented-but-unverified," read `docs/alpha/STATUS.md` first — it's the source of truth, not this file or any of the phase docs. Everything below assumes `NEXT_PUBLIC_BACKEND_ENABLED=1` (Alpha has no localStorage path — it's server-first, Postgres-backed, real accounts only).

## How to add a venue/provider key

1. Find the exact env var name and signup URL in `src/lib/alpha/setupStatus.ts`'s `CREDENTIAL_REQUIREMENTS` — this is the one source of truth Alpha itself reads (`/alpha`'s getting-started card and needs-setup panel call `GET /api/alpha/health`, which surfaces exactly this list with `configured: true/false`).
2. Set it in `.env.local` for local dev, or in the Vercel project's environment variables for production (`vercel env add <NAME>`).
3. Restart `next dev` (env vars are read at module scope, e.g. `getDataStore.ts`'s `BACKEND_ENABLED` pattern — Alpha's adapters follow the same "read once" convention).
4. Verify with a live conformance test rather than assuming the key works: `node --env-file=.env.local node_modules/.bin/vitest run src/lib/alpha/venues/__tests__/<adapter>.test.ts` (or the matching `src/lib/alpha/providers/__tests__/...` for a data provider). The plain `npm run test:unit` never loads `.env.local` by design, so CI stays credential-free — this manual command is the only way to exercise a real key locally.
5. A real per-user credential (not the shared `.env.local` fallback) round-trips through Supabase Vault: `POST /api/alpha/credentials` or MCP's `set_venue_credentials` (`alpha:credentials` scope) calls `alpha_store_secret`; nothing ever reads it back in plaintext except the adapter itself via `alpha_read_secret` at call time (`src/lib/alpha/secrets.ts`).

## How to enable a venue

1. `/alpha`'s Venues section, or MCP's `set_venue` (`alpha:manage` scope), or `PATCH /api/alpha/venues`.
2. Every venue row is auto-provisioned **disabled** on first reference (`service.getOrCreateVenue`) — nothing trades until you flip `enabled: true` explicitly. Set `maxStake`/`dailyCap`/`dailyLossStop` at the same time; these are the venue-level risk gate inputs `risk.ts`'s `evaluateIntent` checks alongside the strategy's own caps.
3. `mode` is always `"paper"` or `"demo"` — never set (and the app can never produce) `"live"`. `service.ts`'s `assertVenueModeNotLive` throws if a row or adapter ever reports `"live"`, so a schema-level accident fails loudly instead of silently placing a real-money order — this is enforced, not just documented, see `src/lib/alpha/__tests__/venueModeAssertion.test.ts`.

## How to create and run a strategy

1. `GET /api/alpha/strategy-templates` (or MCP `list_strategy_templates`) lists every registered `strategy_key` with its venue(s), default schedule, and default params — `src/lib/alpha/strategies/index.ts`'s `STRATEGY_REGISTRY` is the single source of truth; adding a new strategy is "write a module, register it here," nothing else needs to know. Current keys: `terminal-ma-cross`, `terminal-hourly-momentum`, `manifold-mean-reversion`, `manifold-longshot-fade`, `manifold-control`, `football-value-1x2`, `football-value-ou25`, `football-line-move`, `football-market-only-control`, `kalshi-cross-venue-divergence`, `bybit-hourly-momentum`, `deriv-synthetic-meanrev`, `polymarket-sim-longshot-fade`, `polymarket-copy-sources`, `manifold-copy-sources`, `copy-random-control`, `learned-from-sources` (a phase-2 stub — does nothing until enough real copies exist to fit against).
2. `POST /api/alpha/strategies` (or MCP `create_strategy`, `alpha:manage`) with a `strategyKey`, `venue`, `budget`, and risk caps (`maxStake`/`dailyCap`/`dailyLossStop`, optional `kellyFraction`/`minEdge`/`maxOdds`/`cooldownMin`). New strategies are created **disabled**, same "opt-in explicitly" convention as venues.
3. Enable it (`PATCH .../[id]` with `enabled: true`, or MCP `set_strategy`) — once enabled and its venue is also enabled, the `alpha-run` cron picks it up on its own schedule (interval-based; cron-expression/event schedules aren't implemented — an unimplemented schedule pushes `next_run_at` out an hour rather than spin-looping).
4. Force an immediate tick without waiting for the schedule: `/alpha`'s "Run now" button, `POST /api/alpha/strategies/[id]/run`, or MCP `run_strategy_now` — this just sets `next_run_at = now()` so the next `alpha-run` tick (≤1 min away) picks it up. There is exactly one runner (`runDueStrategies` in `runner.ts`) regardless of which door triggered it.
5. Every intent a strategy produces goes through the same chokepoint as a human's manual order or an MCP `place_intent` call: `risk.ts`'s `evaluateIntent` (7-point gate: kill switch, venue/strategy enabled, budget, min-edge, max-odds, cooldown, daily caps) → `service.executeIntent` (logs to `alpha_decisions`, calls `venue.place()`, logs to `alpha_orders`, records spend). Nothing bypasses this.
6. Watch it: `/alpha`'s decisions feed, `GET /api/alpha/decisions`, or MCP `list_decisions`/`get_runs`/`get_run` — every run (including a zero-intent tick, which is a normal outcome, not a bug) leaves an `alpha_runs` row with a `log`.

## How to read the leaderboard / strategy stats

- `/alpha`'s proposals inbox and strategy cards surface Level 2 scoring computed nightly by `evaluate.ts`: ROI confidence interval (bootstrap), hit rate, drawdown, Sharpe, and CLV where the venue supports an honest probability reading (not every venue does — `zoqo-terminal`/`bybit-demo`/`deriv-virtual` correctly report `null` CLV rather than a fabricated number).
- MCP `get_strategy_stats` / `get_health` (`alpha:read`) return the same numbers programmatically.
- Copy-trading strategies additionally get a nightly **copy-gap** metric (`alpha_events` rows with `payload.kind: "copy_gap"`) comparing our realized outcome distribution against the source's replicated decisions — `MCP get_copy_gap` computes the same thing on demand. Read the honest caveat before trusting a real candidate's score: detected fills are logged **unresolved** (no settlement-feed link back to the source's own win/loss yet), so `scoreSource`'s skill components under-score every real candidate until that's built — `copyability` and history-length still score correctly today.
- A strategy's weekly walk-forward param search (`paramSearch.ts`) never self-applies — it proposes via `alpha_events`, and only `apply_proposal` (ownership-checked) moves a proposed param set into a live strategy.

## How to kill everything

- **Global kill switch**: `/alpha`'s Kill switch card, `PATCH /api/alpha/settings` (`{killSwitch: true}`), or MCP `set_settings`. This is checked first in `risk.ts`'s gate — every strategy, every venue, stops accepting new intents the instant it flips, no restart needed. Open positions are untouched (kill switch stops new decisions, it doesn't force-close existing ones) — settle or cancel those separately if needed.
- **One strategy**: `POST /api/alpha/strategies/[id]/pause` or MCP `set_strategy({enabled: false})` — logs an `alpha_events` `paused` row with a reason. `evaluate.ts` also auto-pauses a strategy whose ROI confidence interval's upper bound goes negative (a real losing strategy, not just bad luck) — same event kind, `paused_reason` set automatically.
- **One venue**: disable it (`PATCH /api/alpha/venues`) — every strategy targeting that venue fails its risk gate on the "venue enabled" check until re-enabled.
- **One open order**: MCP `cancel_order` (no UI route for this yet — MCP-only) where the adapter supports it (`adapter.cancel` is optional — most venues here are paper/simulated with nothing resting to cancel; a venue without it returns a typed "does not support cancelling" error rather than throwing).
